# HydroPulse AI — Jharkhand River Health Monitoring System

Persistent rules for every agent session in this repo. Keep answers/commits focused; do one phase at a time.

## 1. Mission
Build an end-to-end, deployable system that (a) forecasts river discharge/flood risk 1–7 days ahead, (b) tracks drought/low-flow stress, and (c) scores river water-quality "health", for Jharkhand basins (Damodar, Subarnarekha, plus Konar, Barakar, Kharkai, Koel as extensions). Output: Flask API + interactive map dashboard + reproducible ML pipeline. Owner: Om Kumar (MCA, Amity Ranchi). Audience: examiners, interviewers, recruiters — so rigor and honesty beat flash.

## 2. Integrity rules (non-negotiable)
1. NEVER fabricate data, stations, coordinates, CWC station codes, flood events, or metrics. Discover from a source or mark `verified: false` in `config/stations.yaml`.
2. Every dataset row/file carries provenance: `observed | model_reanalysis | forecast | synthetic`. Synthetic data is allowed ONLY for unit tests and an explicit demo fallback, and the UI must show a visible "DEMO DATA" badge.
3. Metrics in README/reports are generated by scripts into `reports/metrics.json`; docs read from it. Never hand-type a number.
4. If a source is unreachable: log it, use the last cache, flag staleness in the API/UI. Never silently substitute synthetic data.
5. GloFAS discharge is MODEL output, not a gauge reading. Say so wherever it is used as a training target.
6. No secrets in git. Use `.env` + `.env.example`.
7. The system is advisory. Show a disclaimer: official warnings come from CWC / Jharkhand disaster management authorities.
8. APIs change. Before coding against any external API, web-search its current docs, and cite the URL in `docs/DATA_CARD.md`.

## 5. Data sources (priority + fallback)
| Need | Primary | Notes |
|---|---|---|
| Weather (rain, temp, humidity) | Open-Meteo forecast + historical archive (ERA5) | No key; cache responses |
| River discharge | Open-Meteo Flood API (GloFAS v4, ~5 km, daily, 1984→ + forecast up to 210 d) | Point must lie ON a river cell; API returns the largest river in the ~5 km cell. Implement a `snap_to_river()` that scans a small grid around each station and picks the cell with the highest mean discharge. Reanalysis history ends mid-2022 — handle the gap explicitly |
| Observed gauges | India-WRIS / CWC FFS (via `hydroswift` or portal exports) | Optional, may be sparse; use for validation/bias-correction where available |
| Water quality | CPCB NWMP monthly records (Jharkhand SPCB) as CSV in `data/raw/wq/` | pH, DO, BOD, COD, conductivity, turbidity, fecal coliform; schema-validated on load |
| Static attrs | SRTM elevation, catchment area, land cover | Optional; enables multi-station "entity-aware" model |

## 6. ML rules
**Flood task.** Predict discharge at t+1…t+7 d per station; derive alert levels from `config/thresholds.yaml` (default percentile-based: Watch ≥P90, Warning ≥P95, Danger ≥P99 of station history; replace with official CWC danger levels when verified).
**Drought task.** SPI-1/3/6 from rainfall (gamma fit) + low-flow flag when discharge < station Q90 (historic).
**Water-health task.** Weighted-arithmetic WQI + classification against CPCB designated-best-use classes A–E (verify criteria against CPCB's official table before coding). Trend + seasonality view per station.
**Method discipline.**
- Baselines FIRST: persistence, climatology, ridge/LightGBM. LSTM must be compared honestly; if it doesn't win, report that.
- Preferred design: hybrid "GloFAS forcing + local ML correction" (LSTM/LGBM learns residual/bias of GloFAS per station). Also try one multi-station LSTM with static attributes or station embeddings.
- Chronological splits and blocked time-series CV only. No shuffling. Scalers/thresholds fit on train only. Features use past data only (leakage test required).
- Metrics per horizon: NSE, KGE, RMSE, MAE. Alert metrics: POD, FAR, CSI, F1, PR-AUC, peak-timing error, lead time.
- Uncertainty: quantile outputs (P10/P50/P90) or MC-dropout; show the band in the UI.
- Explainability: SHAP/permutation importance; the UI must answer "why is this station red?".
- Seeds fixed; each run logs config, data hash, git SHA, metrics to `reports/runs/`.
- Validate against `data/events/historical_floods.yaml`. Each event MUST cite a source URL found via web search; do not invent events.

## 7. API contract (v1, JSON, OpenAPI docs at /docs)
`GET /api/v1/health` · `/stations` · `/stations/{id}/forecast?days=7` · `/stations/{id}/history` · `/risk/map` (GeoJSON) · `/water-quality/{id}` · `/drought/{id}` · `/alerts` · `/model/metrics`.
Rules: schema validation, consistent error envelope, request timeouts, response caching, `generated_at` + `data_provenance` + `is_stale` on every payload, rate limiting, CORS configured explicitly.

## 8. Dashboard rules
- Leaflet map, station markers coloured by risk with icon + text (colour-blind safe, not colour alone).
- Station panel: hydrograph (observed/model + forecast band), alert level, SPI/drought status, WQI gauge + class, feature-importance "why".
- Always visible: last updated time, provenance badge, advisory disclaimer.
- English/Hindi toggle for alert text. Mobile responsive. Keyboard accessible. Lighthouse accessibility ≥ 90.
- Verify visually: run the app, open it in the browser, capture a screenshot artifact before declaring a UI phase done.

## 9. Quality gates (a phase is done only when ALL pass)
1. `ruff check` clean, type hints on public functions.
2. `pytest` green, ≥80% coverage on `src/hydropulse/` (core logic: metrics, SPI, WQI, leakage test, API contract).
3. Docs updated: README, `docs/ARCHITECTURE.md` (Mermaid), `docs/MODEL_CARD.md`, `docs/DATA_CARD.md`, `docs/LIMITATIONS.md`.
4. Conventional commits, small and frequent (`feat:`, `fix:`, `test:`, `docs:`).
5. A Walkthrough artifact summarising what changed, how it was verified, and known gaps.

- Prefer boring, readable code over clever code; docstrings explain *why*.
- Surface assumptions and limitations explicitly; write them into `docs/LIMITATIONS.md`.
